## User story mapping

| ID | Story | Priority | Spec scenarios | Independently testable when |
|---|---|---|---|---|
| US1 | Persistent side-panel workspace | **P1** | 1, 2, 3, 7 | panel opens, survives navigation, renders the full preview |
| US2 | Real Google sign-in | **P1** | 5, 6 | sign-in yields a session; generate/push stop returning 401 |
| US3 | Capture from the page | P2 | 4 | capture prefills editable fields; restricted pages fail gracefully |
| US4 | Full restyle on shared tokens | P2 | — (FR-015, SC-007) | every screen matches the dashboard; no inline `:root` remains |

US2 is P1 alongside US1 because the DEBUG stub-user fallback was removed backend-side
(`backend/app/api/auth.py:63`) — without sign-in, the panel's generate/push path 401s and US1 cannot
be verified end to end. See plan.md, "Second constraint discovered".

## Wave sequencing (file-overlap safe)

Tasks inside a wave touch **disjoint files** and may run in parallel (`[P]`). Waves are strictly
ordered. No file appears in two concurrent tasks.

```
Wave A  tokens.css · auth.js · lead-api.js · capture.js        (4 new files, no overlap)
   │
Wave B  config.js → manifest.json → background.js              (wiring; manifest+bg are coupled)
   │
Wave C  sidepanel.html + sidepanel.js                          (the workspace; needs A+B)
   │
Wave D  popup.{html,js} ‖ options.{html,js}                    (two disjoint pairs)
   │
Wave E  verification + docs
```

No user story can be verified until these exist. All four files are new; none overlap.

- [ ] **T053** [P] Create `extension/tokens.css` — port the custom properties from `web/src/index.css` (`--bg`, `--surface`, `--surface-2`, `--border`, `--text`, `--muted`, `--accent`, `--accent-2`, `--accent-3`, `--danger`, `--radius`, `--font-sans`, `--mono`) plus shared base/component classes (buttons, inputs, labels, cards, status pills) at the dashboard's 15px/1.5 base. Add a header comment naming `web/src/index.css` as upstream (research R-006, NFR-008)
- [ ] **T054** [P] Create `extension/auth.js` exposing `BDAuth` with `signIn`, `signOut`, `getSession`, `validate`, `authHeaders` per `contracts/internal-contracts.md`. `signIn` uses `chrome.identity.launchWebAuthFlow` with `response_type=id_token`, `scope=openid email profile`, a `crypto.randomUUID()` nonce, and `chrome.identity.getRedirectURL()`; parses the URL **fragment**; verifies the nonce round-tripped; exchanges via `POST /api/auth/google`; stores JWT + user + `expires_at`. Never log token values (NFR-006)
- [ ] **T055** [P] Create `extension/lead-api.js` exposing `BDApi.buildInput/enrich/push/health`. Copy the request shape **verbatim** from `extension/popup.js:55-67` including the required-field guards and `undefined` omission of empty optionals. - [ ] **T056** [P] Create `extension/capture.js` exposing `BDCapture.fromActiveTab()` and the pure `BDCapture.merge(pageContext, formValues)`. **Checkpoint**: the four modules load without error in a scratch extension page.

## Implementation strategy

**MVP = Wave A + Wave B + US1 + US2** (T052-T065). That delivers the actual complaint — a roomy,
persistent panel — and repairs the 401 that currently makes the extension non-functional. US3
(capture) and US4 (restyle) are additive and can land after the MVP is verified.

**Verification gate**: T072-T074 are not optional sign-off theatre — SC-006 (no CORS errors) and
SC-008 (backend + web still green) are the two ways this feature could silently break things outside
`extension/`.
